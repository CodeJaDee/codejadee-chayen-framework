# PostgreSQL partitioning and safe schema migrations

Stack detail for schema changes on PostgreSQL. Read
[postgresql.md](postgresql.md) first and use it with the migration recipe
and the database safety checklist. Migrations run first on a test or
disposable database; shared and production databases need approval, and no
destructive migration runs there from this guidance.

## Check the repository first

| Area | What to look for |
|---|---|
| Migration tool | EF Core migrations (`UseNpgsql`), Alembic, Django, Flyway, Liquibase, Prisma Migrate, Drizzle Kit, `node-pg-migrate`, or SQL files |
| Transaction mode | Whether each migration runs in a transaction, and how the tool disables it for `CONCURRENTLY` statements |
| Table sizes and traffic | Row counts, write rate, long-running transactions, replicas and logical replication |
| Partitioning | `pg_partitioned_table`, partition bounds, default partitions, partition creation jobs (`pg_partman` or the application) |
| Deployment | Who applies migrations to shared environments, and whether the app migrates at startup |

## Declarative partitioning (postgres-partitioning)

**Applies when:** designing, adding, maintaining, or querying range, list,
or hash partitioned tables on PostgreSQL, or converting a large table to a
partitioned one.

**Not when:** the table is small or queries do not filter on a natural key
(partitioning adds cost without pruning), or the engine is not PostgreSQL.

**Version notes:** declarative partitioning is 10; default partitions, hash
partitioning, and indexes on partitioned tables 11; foreign keys referencing
partitioned tables 12; `DETACH PARTITION CONCURRENTLY` 14. Check the
installed release notes before relying on newer partition commands.

**Steps:**

1. Justify partitioning with measured needs: pruning by a key most queries
   filter on, cheap retention (detach and drop old partitions), or
   maintenance per partition. Otherwise use indexes.
2. Choose the key and granularity from query predicates and retention;
   every unique constraint and primary key must include the partition key,
   which can change the application's identity rules.
3. Create future partitions ahead of time (a scheduled job or extension)
   and decide on a `DEFAULT` partition; without a matching partition an
   insert fails (`23514`), with a default one it silently collects
   misrouted rows that later block new partitions.
4. Check pruning with `EXPLAIN`: only predicates on the key (with constants
   or parameters the planner can use) prune partitions.
5. Convert an existing large table with a planned, reversible sequence (new
   partitioned table, batched copy or attach of the old table as a
   partition, cut-over) and approval for each shared environment.
6. Test on a disposable database: inserts route correctly, missing ranges
   fail as designed, pruning appears in plans, and retention detaches the
   intended partition.

**Verify:** report PASS, FAIL, or NOT_RUN for routing, missing-partition
behaviour, pruning in `EXPLAIN`, and retention; performance claims need
MEASURED before and after numbers.

## Safe schema migrations (postgres-schema-migrations)

**Applies when:** writing or reviewing a PostgreSQL schema migration in any
tool, especially on large or busy tables, or reviewing SQL generated by EF
Core, Alembic, Prisma, or Django for PostgreSQL.

**Not when:** the migration targets SQL Server (its schema reference) or the
change is a data backfill alone (migration recipe), or no migration tool
manages the schema and the user asked only for design.

**Version notes:** `ADD COLUMN` with a non-volatile default is metadata-only
from 11 (a volatile default such as `random()` rewrites the table); `ALTER
COLUMN TYPE` usually rewrites the table and its indexes; from 12 a valid
`CHECK (col IS NOT NULL)` lets `SET NOT NULL` skip the scan. DDL is
transactional, except statements such as `CREATE INDEX CONCURRENTLY`.

**Steps:**

1. Classify each statement by lock and data effect: metadata-only, table
   rewrite (type change, volatile default), full scan under lock (adding a
   validated constraint), or destructive (drop, narrowing, rename used by
   running code).
2. Plan expand, migrate, contract across releases: add nullable columns or
   new tables, deploy code that writes both shapes, backfill in batches,
   switch reads, and drop the old shape in a later approved release.
3. Add constraints in two phases: `ADD CONSTRAINT ... NOT VALID` (checks
   new rows immediately) then `VALIDATE CONSTRAINT` after an approved
   cleanup of existing violations. Build indexes with `CONCURRENTLY`
   outside the migration transaction.
4. Set `lock_timeout` and `statement_timeout` at the start of migrations so
   a blocked statement fails fast; keep each migration short.
5. Generate SQL with the project's tool and review it for PostgreSQL
   behaviour, including type mappings (for example `timestamp` versus
   `timestamptz`, `numeric` precision) and identifier quoting.
6. Apply, roll back, and re-apply on a test database (container or local
   cluster) with representative data, and time the rewrite steps.

**Verify:** report PASS, FAIL, or NOT_RUN for apply, rollback, and re-apply
on a test database, constraint validation, and lock-timeout behaviour;
production application is a separate approved step, never run from here.

```sql
SET lock_timeout = '5s';
ALTER TABLE orders ADD CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customers (id) NOT VALID;
-- later, after an approved cleanup:
ALTER TABLE orders VALIDATE CONSTRAINT fk_orders_customer;
```

## Commands

```bash
psql "$TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f migration.sql
alembic upgrade head && alembic downgrade -1 && alembic upgrade head   # Alembic projects, test database only
dotnet ef migrations script --idempotent -o migration.sql              # EF Core projects
```

## Pitfalls

- `ALTER COLUMN TYPE` on a large table during business hours.
- A migration without `lock_timeout` waiting behind a long transaction while
  every new query queues behind it.
- Partitioning without pruning, or without future partitions.
- Testing migrations only against SQLite or an in-memory provider.
