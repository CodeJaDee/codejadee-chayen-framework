# Dependency upgrades

Upgrade a package or library to a requested version safely:
- read what changed;
- find the affected usages;
- upgrade with the project's package manager;
- fix breaking changes;
- verify with the project's build and tests.

The library is never replaced by a different one, and the upgrade never
widens silently into other packages. Framework major upgrades go one major
version at a time with the official tooling, and a breaking-change analysis
lists every affected usage before code changes start.

## Inputs

- The package, its current version (from the manifest or lock file), and
  the target version. If none is given, use the latest stable, and confirm
  that it is a major jump.
- The package manager and the lock file, and central version files
  (`Directory.Packages.props`, workspace catalogs).
- The release notes, changelog, or migration guide between the two
  versions, read from the vendor's documentation and cited.

## Procedure

1. **Classify the jump** as patch, minor, or major, using semver as the
   vendor applies it.
   - A major upgrade, or a framework-level package (ASP.NET Core, Angular,
     React, Next.js, Vue, Nuxt, Django), is a risky action: confirm before
     starting.
   - A cross-platform migration (for example .NET Framework to .NET, or
     AngularJS to Angular) is planned first with the architecture skill's
     migration planning. A framework major upgrade on the same platform
     follows the framework section below.
2. **Read the changes between the versions.**
   - Collect the breaking changes, deprecations, new peer dependency or
     runtime requirements (minimum .NET, Node, or Python version), and
     changed defaults.
   - Cite the source.
3. **Find the affected usages:** search the code for the APIs named in the
   breaking changes, and for configuration keys that changed. List them
   before editing.
4. **Upgrade with the tool,** never by hand-editing the lock file:
   - `dotnet add <project> package <Id> --version <v>`, or edit the version
     in `Directory.Packages.props`;
   - `npm install <pkg>@<v>`, `pnpm up <pkg>@<v>`, or `yarn up <pkg>@<v>`;
   - `uv add`, `poetry add <pkg>@<v>`, or editing `requirements*.txt` and
     re-locking with the project's tool.

   Upgrade only the requested package. Upgrade the required peers only when
   the resolver demands it, and list them.
5. **Fix the breaking changes** at each affected usage, following the
   migration guide. If the guide offers a codemod or migration command (for
   example `ng update` migrations), use it and review its diff.
6. **Verify** with the build, tests, and the configured lint and typecheck.
   Also check the runtime-only effects the release notes mention (changed
   defaults, serialization).
7. **Never swap libraries.** If the upgrade is blocked (an incompatible peer,
   an abandoned package), stop. Present the options: stay, upgrade the
   blocker, or replace (with the user's approval). Nothing is replaced
   silently.

### Framework major upgrade (CAP-15-004)

1. **List the hops:** each major version between current and target, the
   official migration guide for each, and prerequisites (runtime, SDK,
   tooling, peer libraries).
2. **Clear warnings first:** fix deprecation warnings on the current version,
   because the next major usually removes those APIs.
3. **Upgrade one major at a time** with the official tooling (`ng update`,
   the .NET Upgrade Assistant, vendor codemods, `npx nuxi upgrade`,
   `django-upgrade`), review its diff, then build and run the tests after
   each hop. Keep each hop as its own commit.
4. **Record the result per hop:** commands, migrations applied, manual fixes,
   and build and test results. Stop at the first hop that fails and report
   it.

### Breaking-change analysis (CAP-15-005)

1. **Collect the breaking changes** from the cited release notes and
   migration guides, compiler errors from a trial upgrade on a branch, API
   compatibility tools where the stack has them, and deprecation warnings.
2. **Find every affected usage:** search for the removed or changed symbols,
   configuration keys, and defaults, and list the files and lines.
3. **Classify each item** by effort (S, M, L) and risk: detected at compile
   time, or only at runtime (reflection, serialization defaults,
   configuration, changed behaviour).
4. **Mark the items static search cannot prove** as needing runtime testing,
   with the test or check that would cover them.

## Outputs

- Updated manifests and a lock file regenerated by the package manager, with
  code changes at each affected usage.
- A summary of the relevant release notes, with the source, and the list of
  peers upgraded with their reasons.
- Build and test results, and the behaviour changes that need runtime or
  manual checking.
- For framework upgrades: a version-by-version plan using official tooling,
  and the applied changes with build and test results per step.
- For breaking-change analysis: a list of breaking changes with affected
  files and the fix for each, and the items that need runtime testing.

## Technology considerations

| Stack | Consideration |
|---|---|
| .NET | Central package management (`Directory.Packages.props`). `dotnet list package --outdated` and `--include-transitive` (needs registry access, so ask). Binding redirects only on .NET Framework. Major ASP.NET Core and EF Core upgrades follow the official migration guides per version. |
| Angular | `ng update <pkg>@<v>` runs the schematics. Upgrade one major version at a time, and keep `@angular/*` packages aligned. |
| React / Next.js / Vue / Nuxt / Vite | Peer dependency ranges block upgrades. Use the vendor codemods (`@next/codemod`, `npx nuxi upgrade`) where documented. Use only the lock file's package manager. |
| Nitro / Elysia | Bun lock files (`bun.lockb` or `bun.lock`) are regenerated by `bun install`. Elysia plugins track the core version. |
| Python | Respect the project's resolver (uv, Poetry, pip-tools). Pydantic v1 to v2 and Django feature releases have official migration notes. Re-run the type checker. |
| SQL drivers and ORMs | Driver upgrades can change defaults, for example TLS defaults in `Microsoft.Data.SqlClient` (`Encrypt=true`). Flag them for runtime checking. |

## Verification

- Only the requested package, plus the listed required peers, changed in
  the manifests. The lock file was produced by the package manager.
- Every breaking change from the cited notes was checked against the code,
  and each affected usage was fixed or reported.
- Build, tests, and the configured lint and typecheck pass with the
  project's commands, or are reported FAIL or NOT_RUN.
- No library was replaced or removed without approval.
- The Angular fixture is upgraded one major at a time with `ng update`,
  building after each step, or the run is NOT_RUN with the reason.
- Two seeded uses of removed APIs in the fixture are found with file
  references.
