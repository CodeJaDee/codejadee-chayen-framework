# Code generation from contracts

Generate or regenerate code from a contract (OpenAPI, GraphQL schema,
protobuf, JSON Schema) with the generator the project already uses. Keep the
generated code separate from hand-written code. Adapt the hand-written code
to the contract changes.

## Inputs

- The contract file, its source (a local file, or a URL the project
  references), and what changed in it.
- The generator and its configuration: the config file, the script in
  `package.json` or the build, and where the output goes.
- The hand-written code that consumes the generated types or clients.

## Procedure

1. **Find the generator.** Look for the configuration and scripts, for
   example:
   - `nswag.json` or NSwag MSBuild targets, Kiota, `openapi-generator`;
   - `orval.config.*`, `openapi-typescript`, `@hey-api/openapi-ts`;
   - `codegen.yml` (GraphQL Code Generator);
   - `buf.gen.yaml` or `protoc`;
   - `datamodel-code-generator`.

   If none exists, ask before introducing one. Propose the tool and the
   output location.
2. **Regenerate with the documented command,** with the generator version
   pinned by the project. Never hand-write or hand-edit generated files.
   Customization goes through generator options or partial and extension
   files.
3. **Review the generated diff.** Summarize the added, removed, and changed
   types and operations. Removed or renamed members are breaking for the
   hand-written callers.
4. **Adapt the hand-written code** to the changes. Keep the adapters thin.
   Do not wrap the generated code in new abstractions unless the project
   already does.
5. **Keep the generated code marked.**
   - Use generated headers or `// <auto-generated>`.
   - Use separate folders.
   - Follow the project's convention for committing generated output, and
     its lint and format exclusions.
6. **Verify** with the build or typecheck and the tests that exercise the
   clients (mocked or contract tests).

## Outputs

- Code regenerated through the documented command, with generated files
  marked and placed where the configuration says.
- A summary of the contract changes, with the breaking ones flagged.
- Hand-written adaptations, and build and test results.

## Technology considerations

| Stack | Consideration |
|---|---|
| .NET | NSwag (`nswag run`, or the MSBuild integration), Kiota (`kiota generate`), or `Microsoft.Extensions.ApiDescription.Client` (`OpenApiReference` items). Server-side OpenAPI generation (Swashbuckle, `Microsoft.AspNetCore.OpenApi`) produces the contract that clients consume. |
| Angular | Generated services from `openapi-generator` (typescript-angular) or `ng-openapi-gen`. Register the providers as the existing code does. |
| React / Next.js / Vue / Nuxt | orval or `openapi-typescript` with `openapi-fetch`. GraphQL Code Generator with the typed document nodes the project uses (Apollo, urql, TanStack Query). |
| Node (Nitro, Elysia) | Elysia can emit OpenAPI from its schemas. Zod-to-OpenAPI or TypeBox schemas may be the source of truth, in which case the contract is generated from the code. |
| Python | `datamodel-code-generator` for pydantic models. FastAPI generates OpenAPI from code, so clients are generated downstream from `/openapi.json`. |

## Verification

- The generator command was run, not hand-written output. The generator
  version matches the project's pinned version.
- Generated files carry generated markers, and live in the configured
  location.
- The build or typecheck passes. The breaking contract changes are listed,
  and each caller was adapted or reported.
- No new generator was introduced without approval.
